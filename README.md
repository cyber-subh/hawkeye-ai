# HAWK AI — AI SOC Analyst Copilot

HAWK AI automates the repetitive parts of a Security Operations Center analyst's
day: correlating raw alerts into incidents, mapping them to MITRE ATT&CK techniques,
generating human-readable incident reports, and answering natural-language questions
about what's happening in the environment.

It runs entirely locally, uses synthetic log data by default so you can try it
without any real infrastructure, and degrades gracefully to template-based logic
if you don't have an Anthropic API key configured.

## What it does

1. **Log ingestion** — accepts security events (failed logins, port scans, file
   access, etc.) either from the built-in synthetic generator or from your own
   log pipeline.
2. **Correlation engine** — groups related raw events (same source IP / user,
   close in time) into incidents, rather than showing analysts a flat list of
   noise.
3. **MITRE ATT&CK mapping** — tags each incident with the relevant attack
   techniques (e.g. `T1110 - Brute Force`, `T1486 - Data Encrypted for Impact`).
4. **Explainability** — every incident includes a plain-English "why was this
   flagged" reason, not just a black-box score.
5. **AI-generated incident reports** — a one-click summary + recommended actions,
   generated by Claude (or a deterministic template if no API key is set).
6. **Analyst copilot chat** — ask questions like "what happened with
   svc_backup?" and get an answer scoped to the current incidents.

## Setup

### 1. Install dependencies

```bash
cd hawkeye-ai/backend
python3 -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 2. (Optional) Enable real AI-generated reports

By default, HawkEye works fully without any API key — incident reports and chat
replies use a deterministic template/keyword-search fallback instead of an LLM.

To enable real Claude-generated reports and smarter chat answers:

```bash
cp ../.env.example ../.env
# edit .env and add your ANTHROPIC_API_KEY
export ANTHROPIC_API_KEY=your_key_here   # or use a tool like python-dotenv / direnv
```

### 3. Run the backend

```bash
cd hawkeye-ai/backend
uvicorn main:app --reload --port 8000
```

The FastAPI backend also serves the dashboard directly — open your browser at:

```
http://localhost:8000
```

That's it. No separate frontend build step, no npm install required.

## Using the dashboard

1. Click **"Generate full attack demo"** — this seeds the database with
   background noise plus five embedded attack scenarios: brute force,
   lateral movement, port scanning, ransomware-style file encryption, and
   C2 beaconing.
2. The top stats strip shows a live summary: total incidents, critical
   count, high-severity count, affected assets, and unique source IPs.
3. The left panel shows correlated incidents, sorted by severity. Use the
   search box to filter by IP/user/asset, or the dropdown to filter by
   severity level.
4. Click an incident to see its MITRE ATT&CK tags, the "why flagged"
   explanation, and the raw correlated events.
5. Click **"Generate report"** to get an AI-written (or template-based)
   incident summary with recommended actions.
6. Use the chat panel on the right to ask questions, e.g.:
   - "What happened with svc_backup?"
   - "Tell me about the ransomware incident"
   - "Which IPs are from outside India?"
7. Click **"Reset"** to clear all logs and start over.


## Dashboard features

- **Threat overview** — severity donut, most-targeted assets, MITRE ATT&CK
  coverage grid, hourly activity chart and noisiest source IPs.
- **Incident triage** — mark incidents as *investigating* or *resolved*;
  the state is remembered in your browser.
- **Detail tabs** — Overview (techniques + event breakdown), Timeline
  (chronological event trail) and AI Report.
- **Export** — download any incident as a plain-text report.
- **Search & filter** — free-text search across IP, user, asset, technique
  and the flagging reason, plus severity chips.
- **Keyboard shortcuts** — `G` run demo, `R` reset, `/` search, `T` theme,
  `J`/`K` move between incidents, `Esc` close.
- **Dark / light themes** — remembered between visits.

## API endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/status` | LLM availability and log count |
| POST | `/api/logs/generate?full=true` | Generate synthetic demo logs |
| POST | `/api/logs/ingest` | Ingest your own logs |
| GET | `/api/logs` | Raw stored logs |
| DELETE | `/api/logs` | Clear all logs |
| GET | `/api/alerts` | Correlated, MITRE-tagged incidents |
| GET | `/api/alerts/{id}` | A single incident |
| GET | `/api/alerts/{id}/report` | AI or template incident report |
| GET | `/api/stats` | Aggregated dashboard analytics |
| POST | `/api/chat` | Ask the copilot a question |

## Feeding in your own logs

Instead of (or in addition to) synthetic data, POST your own events to
`/api/logs/ingest` matching this schema:

```json
{
  "logs": [
    {
      "timestamp": "2026-07-31T14:22:00",
      "src_ip": "203.0.113.45",
      "user": "jane.doe",
      "asset": "vpn-gateway",
      "event_type": "failed_login",
      "raw_message": "Failed VPN login attempt",
      "geo_country": "RU"
    }
  ]
}
```

`event_type` values the correlation engine and MITRE mapper currently
recognize: `failed_login`, `successful_login_unusual`, `port_scan`,
`lateral_movement`, `privilege_escalation`, `file_encryption`,
`suspicious_outbound`, `phishing_email`, `suspicious_process`,
`file_access_sensitive`. You can extend these in
`backend/services/correlation.py` (severity weights) and
`backend/data/mitre_lite.json` (MITRE keyword mapping).

To connect a real log source (Syslog, Windows Event Forwarding, an EDR
export, a firewall's API), write a small adapter script that reads from
that source, transforms events into the schema above, and POSTs them to
`/api/logs/ingest` on a schedule (cron job, systemd timer, etc.).

## Extending this project

Ideas for taking this further, roughly in order of effort:

- **Smarter correlation**: replace the rule-based grouping in
  `correlation.py` with embedding similarity (sentence-transformers) so
  incidents can be grouped by semantic similarity of `raw_message`, not
  just src_ip/user/time.
- **Smarter MITRE mapping**: same idea — embed the MITRE technique
  descriptions and match against event descriptions with cosine
  similarity instead of keyword lookup, so novel event types still get
  mapped reasonably.
- **Persistent incident state**: currently incidents are recomputed on
  every request from raw logs. Add an `incidents` table so analysts can
  mark incidents as "resolved," "false positive," etc., and that state
  survives.
- **Authentication**: add a login layer (FastAPI has good support for
  OAuth2/JWT) before exposing this beyond localhost.
- **Real-time streaming**: swap the polling-based dashboard for a
  WebSocket connection so new incidents appear instantly.
- **Multi-user support**: track which analyst is looking at which
  incident, add assignment/handoff features.

## Notes on the demo data

The synthetic log generator is intentionally designed to produce clearly
identifiable attack patterns (a real attacker won't be this obvious) so
you can verify the correlation and MITRE mapping logic is working
correctly. For a portfolio piece, this is normal — pair it with a
description of how you'd validate against real SOC data if asked in an
interview.
